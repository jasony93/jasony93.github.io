## 1. 검토 기준과 참조 문서

- 검토 축 (마케팅팀 요청): (a) 구현 난이도·규모 (b) 2차 범위 정합성 - 부가
  지표·확장은 사용자 재문의 필수(PRD 4절 확정) (c) 데이터 라이선스 영향
  (d) 현 MVP 구조(정적 사이트·서버리스·의존성 0)와의 충돌 여부.
- 참조: 마케팅팀 초안 `docs/marketing/2026-08-03-bm-improvement.md`,
  설계 문서 `docs/development/2026-08-03-adr-premium-design.md` (정적 웹 +
  Python 파이프라인, 서버 사이드 없음), PRD
  `docs/planning/2026-08-03-adr-premium-prd.md`.
- 현 구조 요지: 파이프라인(fetch_data.py)이 정적 JSON을 생성하고 웹은 읽기만
  한다. 소스 교체는 수집부 한정, 화면·계산은 영향 없음. 이 구조가 P1~P5 대부분을
  저비용으로 만들고, P7~P8을 고비용으로 만든다.
- 종목 수: 확정 표 기준 **11종목**(한국 ADR 9 + 삼성전자 GDR + TSMC). PRD 본문의
  "12종목" 오기는 2차 개정(관리자)에서 이미 정정됨. 본 문서의 비용·호출량 추산은
  11종목 기준.

## 2. P1~P8 항목별 평가

### P1. 뉴스레터 구독 폼 + 주간 요약 자동 생성 (BM-6) - 가능

- (a) 난이도·규모: **하.**
  - 구독 폼: 자체 구현 불필요. 국내 서비스 스티비(Stibee)가 구독 폼을 HTML 코드로
    내보내 임베드하는 방식을 공식 지원하므로 정적 사이트에 그대로 붙는다
    (https://help.stibee.com/pricing/understanding/type ,
    https://simplep.net/how-to-use-stibee/ ). 구독자 명단은 폼 서비스에 위탁되어
    우리 쪽 서버·DB가 필요 없다.
  - 비용: 스티비 무료 스타터는 구독자 500명·**월 2회 발송** 한도. "주간" 발송(월
    4~5회)은 스탠다드 요금제(월 8,900원~) 필요
    (https://blog.stibee.com/stibee-pricing-guide/ ). 초기(구독자 축적기)는 무료
    티어로 격주 발송 시작 -> 구독자·반응 확인 후 유료 전환이 합리적.
  - 주간 요약 자동 생성: 파이프라인이 이미 종목별 스냅샷·히스토리 JSON을 만들므로
    "주간 프리미엄 요약(종목별 현재 %·주간 변동·최대 변동 종목)" 텍스트/HTML
    템플릿 생성 스크립트 1개 추가로 충분. 소규모 (4절 제안 A와 생성기 공유).
- (b) 2차 정합성: 부가 "지표"가 아니라 마케팅 장치다. 다만 PRD 범위 제외
  목록("사용자 계정, 알림")에 인접한 신규 요소 + 비용 발생 가능이므로 **도입
  자체는 사용자 승인 필요** (2차 지표 재문의와는 별개 트랙).
- (c) 라이선스: 주의 1건. 뉴스레터에 시세·프리미엄 수치를 실어 발송하는 것은
  사이트 표시와 같은 "데이터 재배포" 성격이다. yfinance 프로토타입 데이터로 대외
  발송은 불가(비공개 검증 한정 승인 범위). **상업 API 전환 후, 계약서의 재배포·
  파생 데이터 조항 확인 하에 개시**해야 한다. 프리미엄 %(자체 계산값)만 싣는
  구성이 제약을 완화할 수 있으나 단정 불가(추정) - P3와 동일 쟁점.
- (d) 구조 충돌: 없음. 추가 필요물: 개인정보 처리방침 페이지(정적 1장).

### P2. 프리미엄 임계값 알림 - 텔레그램 봇 우선 (BM-1, 리스크 헤지) - 조건부

- (a) 난이도·규모: 방식에 따라 갈린다.
  - **공용 채널 방송형(권장)**: 텔레그램 공개 채널 1개 + 파이프라인 끝에 "고정
    임계값(예: 절대값 5%/10% 돌파, 전일 대비 2%p 이상 변동) 체크 -> Bot API로
    채널에 메시지" 단계 추가. GitHub Actions 스케줄 실행과 결합하면 서버 없이
    성립한다. 난이도 하.
  - GitHub Actions cron의 실측 제약(웹 조사): public 저장소는 무료·무제한이나
    스케줄 실행은 정시 보장이 없고 10~30분 지연이 흔하며, **저장소가 60일간
    활동(커밋 등)이 없으면 스케줄 워크플로가 자동 비활성화**된다(메일 통지 후).
    출처: https://docs.github.com/en/actions/reference/limits ,
    https://dylanbritz.dev/writing/scheduled-cron-jobs-github/ ,
    https://github.com/orgs/community/discussions/185355 . EOD 기반 알림이므로
    수십 분 지연은 허용 가능. 60일 비활성은 운영 체크리스트로 관리(파이프라인이
    데이터 커밋을 만들면 사실상 해소).
  - **개인별 맞춤 임계값**: 사용자 상태(구독자별 설정) 저장이 필요해 서버리스
    정적 구조를 벗어나기 시작한다. 브라우저 푸시도 푸시 서버·구독 관리가 필요.
    이 형태는 P7과 같은 단계로 미뤄야 한다.
- (b) 2차 정합성: **알림은 PRD 4절 범위 제외 명시 항목이다. 공용 채널형이라도
  기능 추가이므로 사용자 재문의 필수.** 본 문서는 "재문의 시 공용 채널형을 1안
  으로 제시"까지만 권고한다.
- (c) 라이선스: 메시지에 가격을 포함하면 P1과 동일한 재배포 쟁점. 프리미엄 %와
  사이트 링크만 발송하는 구성을 기본안으로 권고(그래도 계약 확인 필요, 추정).
- (d) 구조 충돌: 공용 채널형은 없음. 개인화형은 충돌.

### P3. 임베드 위젯 (BM-2) - 조건부 (기술 쉬움, 계약이 관건)

- (a) 난이도·규모: **하.** iframe 방식 권고 - `embed.html?symbol=SKHY` 형태의
  경량 정적 페이지 1장을 추가하고 기존 meta.json을 재사용하면 된다. 스크립트
  임베드는 호스트 사이트 CSS/JS와의 간섭 처리 부담이 있어 초기에는 iframe이
  단순하다. "계산값(프리미엄 %)만 표시 모드"는 같은 JSON에서 표시 필드만 줄이면
  되므로 기술적으로 자명하다.
- (b) 2차 정합성: 부가 지표는 아니지만 신규 공개 화면이므로 범위 추가 - 사용자
  승인 필요.
- (c) 라이선스: **최대 관건 - 마케팅팀 판단(재배포 해당 가능성 높음)에 동의.**
  제3자 사이트에 우리 데이터를 표시하는 것은 원천 계약상 재배포로 해석될 여지가
  크고, 파생 데이터(계산값)에 대한 권리도 계약마다 다르다. 상업 API **계약서의
  derived data / redistribution 조항 확인 전에는 배포 불가**로 못 박는다.
  yfinance 단계에서는 어떤 형태로도 불가.
- (d) 구조 충돌: 없음. 정적 호스팅 그대로 서빙 가능.

### P4. 제휴 링크/배너 슬롯 + 증권사 비교 가이드 (BM-4) - 가능

- (a) 난이도·규모: **하.** 가이드 페이지는 정적 콘텐츠. 슬롯은 기존 D8(광고
  슬롯) 설계와 통합 가능 - 슬롯 컴포넌트에 타입(adsense / affiliate / sponsor)을
  두고 설정으로 교체하는 구조를 권고한다. 심의필 소재는 증권사 제공 이미지+링크의
  정적 게재라 구현 부담이 없다.
- (b) 2차 정합성: 데이터 기능이 아니므로 2차 지표 재문의 대상은 아니다. 다만
  수익화 장치 가동 자체가 "마케팅 전략 확정 후"로 묶여 있으므로 게재 개시는
  사용자 승인 사항.
- (c) 라이선스: 시세 데이터와 무관 - 영향 없음. 대신 금소법 등 광고 규제 검토가
  필수(마케팅팀 지적 동의). 이는 제품 구현이 아닌 관리자·법무 확인 트랙.
- (d) 구조 충돌: 없음.
- 콘텐츠 페이지 확대(마케팅 1.1절)와 겹치므로 4절 제안 A(자동 생성 리포트
  페이지)와 함께 묶으면 개발 공수가 준다.

### P5. 데이터 소스 조합 교체 - 조건부, 상세는 3절

핵심 결론 먼저: 마케팅팀 절감 시나리오("KRX·TWSE·환율 무료 공식 + 미국만 유료
최저가 = 월 $20~35")는 **"무료 공식 API의 상업 이용 허용" 전제가 성립해야 하는데,
KRX는 조사 결과 상업 이용 금지 조항이 확인(2차 출처)되어 성립하지 않을 가능성이
높다.** USD/TWD 환율도 공공 무료 소스에서 확인하지 못했다. 따라서 절감 하한은
재계산이 필요하며, "전 시장 커버 유료 1개" 구조가 오히려 단순·저렴할 수 있다.

- (a) 교체 난이도: 중. 설계 문서 2절 구조상 수집부(fetch_data.py)만 교체하면
  되나, 현재 yfinance 단일 소스 전제이므로 소스별 fetcher 모듈화 + 소스 간 정합
  (날짜 그리드, 통화 단위, 심볼 매핑) + 소스별 장애 처리(기존 fetch_error 구조
  확장)가 추가된다. 소스 3~4개 병행은 장애 지점이 그만큼 늘어난다(마케팅팀도
  인지한 단점 - 4절 제안 C 참고).
- (b) 2차 정합성: 2차 지표 아님. PRD 6절-1·2(예산·LSE 라이선스)에 종속 -
  **비용 발생이므로 사용자 승인 필요.**
- (c) 라이선스: 이 항목 자체가 라이선스 대응 작업이다.
- (d) 구조 충돌: 없음(파이프라인 내부 교체, 웹·계산 로직 무변경).
- SMSN(삼성전자 GDR) 보류 옵션의 구현 비용: 설정 파일(tickers.json)에서 종목
  제거 + 노출 순서 조정뿐 - **구현 비용은 극소**. 단 "전 종목 진행"은 사용자
  확정 사항이므로 보류 결정은 **사용자 재승인 필요**하며, 기획팀 의견으로는 LSE
  커버리지·추가 비용 견적을 받기 전에 보류를 결정하는 것은 이르다.

### P6. 대만 종목 확장·야간 시세 계열 - 평가만 (확정하지 않음)

- 대만 ADR 추가(UMC, ASE 등): (a) 파이프라인·설정 구조상 종목 추가는 저비용 -
  주 비용은 전환비율 1차 출처 확인(종목당 조사 작업)이다. (c) TWSE 소스 재사용,
  미국 DR API 심볼 추가 수준. (d) 충돌 없음.
- 야간 시세 계열(장중/실시간 환산): (a)(d) 현 EOD·정적 전제와 **충돌** - 실시간
  시세 수급(더 비싼 라이선스)과 갱신 주기 단축(정적 재생성 또는 클라이언트 직접
  호출)이 필요해 비용·구조 모두 크게 바뀐다.
- (b) **둘 다 2차 범위다. PRD 4절 약속대로 사용자 재문의가 필수이며, 본 문서는
  로드맵 배치와 우선순위 의견까지만 낸다**: 재문의 시 "대만 ADR 추가(저비용) 우선,
  야간 시세는 별도 타당성 검토 후" 순서를 1안으로 제시할 것.

### P7. 계정·결제·유료 구독 (BM-1) - 충돌, 장기 보류

- 인증 서버, 결제(PG) 연동, 구독자별 권한 분리, 유료 기능용 실시간 데이터 계약이
  모두 필요해 정적·서버리스 구조를 전면 이탈한다. 고정비 구조(현 월 수십 달러
  수준)가 근본적으로 바뀌므로, 재방문층·구독 수요가 실측으로 검증된 뒤(3단계
  이후) 별도 아키텍처 검토로 다룬다. 로드맵 배치만 하고 상세 설계는 하지 않는다.

### P8. 데이터 API 엔드포인트 (BM-3, BM-7) - 충돌, 장기 보류

- API 서버·키 발급·과금·사용량 제어가 필요해 정적 구조를 벗어나고, 원천 데이터
  재배포 계약 쟁점이 P3보다 엄격하다(원천 시계열 제공에 가까움).
- 참고: "정적 JSON을 출처 표기 조건 무료 공개" 같은 저비용 중간 형태도 기술적으론
  가능하나 이 역시 재배포라 계약 확인 전에는 불가. B2B 수요(언론 인용 등)가 실제
  발생하면 그때 계약 조건과 함께 재검토. 장기 보류.

## 3. P5 상세: 데이터 소스 조합 교체 (손익 직결)

### 3.1 KRX 정보데이터시스템 Open API - 일별 종가 제공 확인, 상업 이용은 금지 조항 확인(2차 출처)

- 제공 데이터: KRX Data Marketplace OPEN API에 주식 **일별매매정보**(유가증권·
  코스닥) 서비스가 존재하며 종가를 포함한 일별 시세를 제공한다. 데이터는 대체로
  2010년 이후 제공. 공식 포털: https://openapi.krx.co.kr/ (서비스 목록:
  https://openapi.krx.co.kr/contents/OPP/INFO/service/OPPINFO004.cmd ).
- 호출 제한: 일 10,000콜 수준으로 안내됨(입문 가이드 2차 출처:
  https://bbangpower-blog.blogspot.com/2025/05/krx-api.html ). 우리 용도(11종목 x
  일 1회)에는 충분.
- **상업 이용: 같은 2차 출처에서 "API 결과를 이용한 상업적 이익 추구 금지" 류의
  약관 조항이 확인된다.** 공식 소개 페이지에는 약관 원문이 노출되지 않아(직접
  조회 시도, 로그인/가입 후 약관 확인 필요) 1차 확인은 못 했다. **가입 후 약관
  원문 서면 확인이 선행 과제이며, 확인 전까지 "KRX 무료 API로 상업 사이트 운영
  가능"을 전제로 한 절감 시나리오는 채택하면 안 된다.**
- 성립하지 않을 경우의 대안: 미국+KRX(+LSE)를 함께 커버하는 유료 API 1개(EODHD
  등)로 통합 - 3.4 참고.

### 3.2 환율 - USD/KRW는 공공 무료로 확정 가능, USD/TWD는 미확인

- USD/KRW: 한국은행 ECOS Open API가 원/달러 일별 환율(주요국통화의 대원화환율,
  통계코드 731Y001)을 공식 제공한다 ( https://ecos.bok.or.kr/api/ ). 히스토리

  PRD 3.4절과 동일 입장).
- 한국수출입은행 환율 API: 일 1,000콜 제한, 인증키 발급제
  ( https://www.data.go.kr/data/3068846/openapi.do ). 일 1회 고시 환율로 보조
  소스 적합.
- **USD/TWD(또는 KRW/TWD)**: ECOS(731Y002 대미달러환율 계열)와 수출입은행의 대만
  달러 포함 여부를 이번 웹 조사에서 확인하지 못했다(항목 목록이 검색으로 노출되지
  않음 - 미확인). 대안 후보: (i) 유료 주가 API의 부속 FX 엔드포인트(EODHD 등 -
  가장 단순) (ii) 크로스레이트 계산(KRW/USD와 KRW/TWD로 도출 - KRW/TWD 소스 확인
  필요, 시장 환율과의 오차 검증 필요) (iii) 대만 측 공공 소스. **API 키 발급 후
  항목 목록 실조회로 확정해야 한다(개발팀 착수 전 확인 과제).**
- 참고: 현 프로토타입 환율은 Yahoo 단일 소스로, ECOS와의 교차 검증이 설계 문서
  7절-6에 과제로 남아 있다 - 소스 교체 시 함께 해소된다.

## 4. 기획팀 자체 제안 (마케팅팀 초안에 없는 제품 관점)

- **제안 A - 데이터로 콘텐츠 페이지를 자동 생성**: 마케팅팀은 가이드 페이지
  8~10편 확대(수기 작성)를 제안했는데, 파이프라인이 이미 매일 수치를 만들므로
  **종목별 "프리미엄 리포트" 정적 페이지(전환비율·예탁은행·전환 절차 해설 +
  최신 수치·주간 변동 자동 삽입)를 템플릿으로 생성**하면 콘텐츠 페이지 수 확대와
  SEO 랜딩을 개발 공수 최소로 달성한다. P1 뉴스레터 템플릿과 생성기를 공유해
  한 번 만들어 두 곳에 쓴다.
- **제안 B - 지출 시작과 수익 장치 가동의 동기화**: 상업 API 계약(고정비 발생)
  전에 비용 0 준비물(P4 가이드 원고, P1 구독 폼(무료 티어), 후원 버튼(BM-9),
  개인정보 처리방침, 광고/제휴 슬롯 컴포넌트)을 전부 만들어 두고, **계약 체결과
  동시에 일괄 공개**한다. 고정비가 나가는데 수익 장치가 없는 적자 구간을
  구조적으로 단축하는 출시 순서 조정이다.
- **제안 C - 소스 병행 최소화**: 마케팅팀 1.2절의 "무료 3~4개 + 유료 1개" 병행은
  월 몇 달러 절감 대비 장애 지점·운영 부담 증가가 크다. KRX 약관 확인 결과에
  따라 "유료 1개 + 공공 1개(검증용)"로 소스 수를 줄이는 안을 기본으로 비교
  검토할 것 (3.4 참고).
- **제안 D - 자동 갱신(D5)의 무료 실현 경로 확정**: GitHub Actions 스케줄로
  파이프라인 일 1회 실행 + 정적 호스팅 배포면 서버 비용 0으로 자동 갱신이 된다.
  단 운영 유의 2건 - 스케줄 지연(10~30분 일반, EOD 용도라 허용 가능), 60일
  무활동 시 스케줄 자동 비활성(P2 (a) 출처 참조) - 을 운영 체크리스트에 포함.
